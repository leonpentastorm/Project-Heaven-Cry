It records the replay scenario `proving-4v10-boss` (4 v 10, enemy AI on) and times, on the states that replay handed to

## What the measure said

**The review's premise was wrong for this engine.** The state copy is not the cost: the working copy of a 92 KB
mid-fight state is about 0.45 ms of an 18 ms action (2 to 3%), and the per-action migration pass is 0.006 ms (every
migration but two already returns at once on its revision stamp). The cost was the **sight test**: `sideSeesUnit` was
53% of all apply time, because each eye asked again what does not depend on the eye:

- `seenRangeOf(cb, t)` (the looked-at unit's `seen_range`), which asks `statHeard`, which walks every unit's
  conditions and items: once per eye, so units x units x condition rows per sight question;
- `sightBlockers(cb)` (a new Set of every wall, closed door, smoke tile and cover unit), built per question even when
  no eye was in range, and per tile by area code (`outburstArea`, `reachTiles`, the Evoke tiles, a turret's aim);
- `condStatRows(stat)` made a new array on every `statHeard` call;
- `standable()` walked the map's solid, cover and full lists with `includes()` (hundreds of tiles) on every path step,
  and split each key into two arrays.

## What changed (all behaviour-free; the 29 replays are the proof)

1. `combat.ts` `sideSeesUnit`, `visibility`, `seenIds`: the walls and the target's seen_range are worked out once per
   question, when first needed (`once`), and shared by the eyes; `seenIds` shares the walls across its targets.
   `unitSees` and `eyeReach` take them as optional arguments (one rule still: `eyeReach` is the one sight range).
2. `magic.ts` `outburstArea`, `actions.ts` `reachTiles`, `sigil.ts` (the Evoke-tile list, `turretAim`): the walls once
   per call, not per tile.
3. `effects/triggers.ts`: `condStatRows` returns the index's own list, made once per condition-row version.
4. `combat.ts` `standable`: the map's tile lists as sets (a WeakMap per list, rebuilt if the list's length changes),
   and the key read without `split().map()`; `magic.ts` `XY` the same (any key with other than one comma still goes
   through `split`).
5. `game.ts` `workingCopy`: `jsonCopy`, a structural copy with JSON's exact rules (undefined, functions and symbols
   dropped in objects and null in arrays, NaN/Infinity to null, -0 to 0, key order, `toJSON` and non-plain objects
   through JSON itself). On the repo's three largest saved fights: 0.30 / 0.27 / 0.22 ms with JSON, 0.11 / 0.10 / 0.09 ms
   with `jsonCopy`, and `JSON.stringify` of the two copies is identical. Not exported.

## The migration gate: measured, and left as it is

Call sites: `apply()` runs ten `migrateCharacter*` per sheet on every action; `migrateLoaded` runs on a host's load
and snapshot (rare) and on a **guest's every view** (`apps/web/src/game/store.ts` line 182: once per host action).
Measured: the per-action pass costs 0.006 ms for four sheets, `migrateLoaded` 0.012 ms per view (0.13 ms on the first,
colder run). Eight of the ten already return on a revision stamp (`sigilRev`, `soulRev`, `classRev`, `focusRev`,
`faithRev`, `mpRev`, `hpRev`, `figRev`); `migrateCharacterItems` and `migrateCharacterPerks` have no stamp and are a
short scan. A game-wide stamp would put a new field in the saved state (every replay hash moves, and the replay guard's
save-and-load case requires a load to leave the state as it was), and moving the per-action pass to load time would
change when old-save notes appear and miss a sheet that arrives by `char/add`. Neither is worth 0.01 ms. The existing
old-save tests (old-save, step1-ladder, consolidation-032, figments-2, doors3-forks, migrate-items and the lane tests)
go through `migrateLoaded` and `apply` and are green, unchanged.

## Left, and why

- **The enemy AI is now the bulk of a hostile phase** (`aiSoulStep` / `heartBestRelease` / `previewOutburstPlan` about
  20%, `aiSigilStep` / `planLine` / `planEvoke` about 17% of the profile): another lane owns the AI.
- `perks/b.ts` `noteExplored` (a turn_start handler, about 5%): perks are another lane's.
- `preview.ts` `copyFight` uses `structuredClone`; `jsonCopy` would be faster but keeps different values (undefined
  keys, NaN, -0), so a preview could read differently: not changed. 0.4 ms a call.
- `moveBlockers` and `sightBlockers` are still built per call by single-question callers (an attack's line, a move
  plan); a cache across calls needs an invalidation on every object, door, zone and unit change: not local.
- Many other single `lineOfSight` calls without walls (classes/*.ts, game.ts) are one line each: nothing to share.
- The client's `actionVerdict` already memoises `previewAction` per state (`apps/web/src/game/verdict.ts`).
