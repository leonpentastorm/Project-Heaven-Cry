Branch `wip/0.33-online` (from `origin/main` = live 0.32.0 at `7e1f6bd06`). Not merged, not deployed, version not
bumped. No game rule changed (no spec items); notes in `docs/design/tech-plan.md` section 11. No engine file changed.

## Built

1. **Hosting off KV: Workers Static Assets** (`e012502f3`, docs in the hand-off commit).
   - Confirmed on Cloudflare's own pages (20 Nov 2026): Static Assets hold 100,000 files a Worker version on the Paid
     plan (20,000 Free), 25 MiB a file; `run_worker_first` takes a list of paths for which the Worker runs before the
     assets; a `_headers` file in the assets directory sets headers (not served itself; default
     `public, max-age=0, must-revalidate` with an ETag); `wrangler rollback` goes back to any of the last 100 versions
     under 30 days, refused across a Durable Object migration or a deleted binding.
   - `apps/server/wrangler.jsonc`: `assets` (apps/web/dist, SPA fallback, the Worker first for `/room/*`, `/health`,
     `/hf/*`), KV binding gone; the Worker's KV reader (`serveSite`) removed. Durable Objects unchanged (same class,
     same `v1` migration), so rooms and saves are as they were. The dev config already served assets; now the two
     differ only in name.
   - `apps/web/public/_headers`: art, music, sounds and effects a day's cache (as under KV; replaced art carries
     `?v=<hash>`), `index.html` revalidated, `nosniff` everywhere.
   - `tools/deploy_site.py` rewritten: one command (`python tools/deploy_site.py --build`, or `npm run deploy`)
     builds, checks the limits (file count, 25 MiB a file, a note over 20 MiB: the voice model's `.wasm` is 20.6 MiB)
     and `_headers`, and runs `wrangler deploy`. `--dry-run` proved it here: 2,975 files read, bindings ROOMS and
     ASSETS, nothing uploaded.
   - New routine and the rollback: `docs/HANDOFF.md` "Deploy"; `docs/TESTING.md` "Releasing" updated.
   - Proved locally under `wrangler dev` (port 8801): two-players 13 (two new checks: the cache headers, SPA
     fallback and nosniff served by the asset layer; the ping lines), reconnect 9, room 27, plus the suites below.
2. **Connection fixes:** already done in 0.32 (`d2a5a6636`, 0.32-COOP.md item 3): close 4000 stops and offers Take
   over here, the ping and retry timers are cleared on close, host/join closes the old link. Checked in `net.ts` and
   `store.ts`; nothing redone. 0.33 changes the ping only: every 5 s (was 25 s), answered by the room itself.
3. **Server fixes** (`e012502f3`; rules in `apps/server/src/policy.ts`, tested in `apps/web/src/game/netStats.test.ts`):
   - **Guest token:** a guest's first link that brings a token claims its player id's seat (`seat:<pid>`); later links
     of that id must bring it (any player reads every id in the game's player list and could take a seat and its
     view). The client keeps one per room (`store.ts seatToken`). A link with no token is let in only while the seat
     has none (a tab open from before the release).
   - **Host token length:** a new room is claimed only with a 16 to 64 word-character token (an empty token used to
     claim it). The client's is 24.
   - **Coalesced view writes:** views and the save are held in memory and written together by the room's alarm 2 s after
     the first (and at once when the last player leaves); a guest reconnecting reads the held copy first. Before, each
     view was its own storage write (one a player an action). Loss case: the room evicted inside those 2 s; the host
     sends the view again on the guest's check-in and a save every 1.5 s, and keeps its own copy. It also takes a
     storage write out of most relays: a Durable Object holds its outgoing messages while a write is unconfirmed (its
     output gate), so the per-view write could delay the next message to another player.
   - **Purge alarm:** a room nobody has opened for 30 days is emptied (`deleteAll`); rooms from before get their alarm on
     their next connection. The host's browser keeps the game (IndexedDB), so a purged room is re-claimed by its host.
4. **Input delay:**
   - (a) **Measuring tool.** The guest's action nonce comes back on the host's answer (`ack`, with `hostMs`, its own
     time on it); the room stamps `leg` (its clock, action passed on to answer back). `apps/web/src/game/netStats.ts`
     splits the delay into you–room, room–host and host with no clock comparison. On screen: `NetLine.tsx`, a small
     line bottom-left in any room with two or more players ("LINK · room 182 ms · last action 2.41 s (you–room 460 ms ·
     room–host 1.94 s · host 12 ms) · usual 2.30 s"; the host's line reads its own answering time and size). In the
     Report a problem bundle: `net` (every sample with its parts, the pings). The room answers the ping through
     `setWebSocketAutoResponse` (no wake, no duration billed).
   - (b) **Placement:** a host's link passes a location hint from its continent and longitude (`policy.ts placeFor`).
     What it buys: little in the usual case, since Cloudflare already makes an object near its first `get()`, which is
     the host's; it stops a room being made far from both players when a guest's link is first. Rooms never move once
     made. Any place on the guest-to-host way gives the same total, so near the host is right.
   - (c) **Optimistic feedback:** the guest's click shows a white ring where it pressed and a SENDING chip, and the ping
     line says "sending…", from the click to the host's answer (or a refusal, a lost link, the host away; after 10 s
     it says "no answer yet"). Nothing about the game is guessed: the view that comes back is the truth.
   - (d) **Proposal written:** `docs/design/proposals/2026-11-room-referee.md`. Recommendation: not for the delay (it
     saves 20 to 80 ms with the room near the host and slows the host's own actions); measure first.
   - Found on the way: a view weighs 35 to 61 KB of JSON (about 10 KB deflated) over 342 views of two players' stages 1
     and 2; size is not the 2 to 3 s by itself.

## Numbers provisional

- Purge after **30 days** with nobody in the room (`PURGE_MS`).
- Writes coalesced **2 s** after the first (`FLUSH_MS`).
- Ping every **5 s** (`PING_MS`, was a 25 s keep-alive).
- Tokens **16 to 64** characters.
- The "sending" mark gives up after **10 s** (`PENDING_SHOWN_MS`).
- Cache: art and sound a **day** (as under KV).
