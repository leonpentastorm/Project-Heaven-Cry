# 0.33 lane SPEED: client speed (the outside code review's performance work)

Branch `wip/0.33-speed` (from `origin/main` = live 0.32.0). Client only: nothing in `packages/engine`, nothing in room
networking (`net.ts`, the store's room code, `apps/server`), no restyling. No game rules, no data, no spec change.

## Built

1. **The bundle split by screen** (commit `c510b0138`).
   - Each screen's code and template is its own chunk: `apps/web/src/screenChunks/{create,room,main,combat,levelup,ultimate}.ts`,
     loaded through `apps/web/src/screenLoad.ts` (`loadScreen`, `loadedScreen`). The title stays in the entry chunk.
   - **No empty flash:** `App.tsx useShownScreen` keeps the screen on show, drawn from the state it last had, until the
     next screen's chunk is in (three tries, then a toast asking to reload). The chunks a player can reach next are
     loaded ahead (below), so the wait is normally nothing.
   - **The Narrator:** the Anthropic SDK loads on first use (`narrator/anthropic.ts loadSdk`; `explain` and the
     fallback retries read the loaded module).
   - **The Proving Ground:** its panel (`game/sandbox.tsx`) is its own chunk (`screenLoad.ts loadSandbox`); App waits
     for it like a screen's chunk while the room is in the Proving Ground. Its start, leave and invite part moved to
     `game/provingGround.ts` (the title, the room and the header import that; `sandbox.tsx` re-exports it).
2. **The preloader 2.0** (same commit; roadmap "Preloader: wait for load, only the next screen's art").
   `game/preload.ts`: the title's own art at once; nothing else before the window's load event (and the title's art or
   3 s); then, on every screen reached (`warmNext`, called by App), only the next screens' art (`NEXT`, `SCREEN_ART`:
   asset-name prefixes) and code chunks, small sizes, four at a time at low priority; a screen change drops what was
   still queued. Before: the whole library (about 3,000 files, 91 MB) was warmed behind the title on every visit, and
   on a loaded machine the page's load event waited for it. `title-screen.md` section 8 updated; `e2e/title.mjs`
   checks the new behaviour (177 files queued after the title, not 3,000).
3. **Render counts and the probe** (commit `ec0e0d0b4`). `window.__phcRenders` (App and every overlay, counted in
   `App.tsx`), `window.__phcRenderMs` (the screens' own render time, `dc/runtime.tsx`), and
   `tools/perf/fight_render_probe.mjs` (four fight scenarios in the Proving Ground: toast, hover, move, enemy turn;
   `--profile <scenario>` prints a CPU profile's heaviest functions; build with `--minify false` for names).
4. **The fight screen's render costs** (commit `c41e0a11b`).
   - `game/cast.ts castFight`: the same cast for the same game and fight (a WeakMap by fight, checked against the
     game). It made a new fight object on every render, so `commands.ts listFor` (the engine's `actionsFor`) ran on
     every mouse move: 800 ms of a 1.4 s hover sweep.
   - `screens/combat.js`: the copy of the fight with the effects' held HPs is kept while the held HPs are the same;
     the tiles' cover words are kept per fight and foe.
   - **A toast alone renders nothing but the toast:** the overlays are memoised on their props and `v`, a count of
     the store's changes other than a toast alone (a `poke`, which changes nothing, still counts); the screen keeps the
     state it was drawn with (`ScreenHost` memo). A screen whose logic reads the toast opts in with
     `static readsToast = true` (`MainLogic`: the magic workshop's refused Save).
   - `dc/runtime.tsx` memo lists reuse last render's outside values when equal (one comparison a render, not one per
     tile).
   - `game/fx/dom.ts track`: every anchored node's place is read first, then written (it laid the page out once per node,
     every frame: 470 ms of layout in one enemy turn).

## Not built, and why

- **The engine out of the boot chunk.** The title imports the store, the store the engine and every data file: 3.3 MB
  of the 5.3 MB at boot. Splitting it means a store that loads the engine on demand (every `act`, `hostRoom`,
  `migrateLoaded` asynchronous): the room code, which the online lane owns this release. Proposed for after 0.33.
- **The effects layer split** (about 350 KB in the entry chunk). `turnIntro`, `cutIn`, `mapHover`, `sandbox` and
  `combat.js` import pieces of `game/fx` directly; a split needs those seams first (a file split).
- **Fewer map-item comparisons per render.** What is left of a hover render is the combat screen's `renderVals`
  (about 5 ms) and the 676 tiles' memo comparisons (about 5 ms): the tiles' value objects are rebuilt every render.
  Building them per tile only when their inputs change is a larger rework of `combat.js` (a file split is on the
  review's list too).
- **Baseline browser runs.** On this machine, with other lanes running, `origin/main`'s suites stop at `page.goto`
  (the load event waits for its 3,000-image preload); this branch's do not. So the fight-panel failures below could not
  be compared with a baseline run.

## Primitives added

None in the engine. Client pieces (general, no item ids): `screenLoad.ts` (`loadScreen`, `loadedScreen`, `chunkOf`,
`loadSandbox`, `loadedSandbox`), `preload.ts` (`NEXT`, `SCREEN_ART`, `nextArt`, `titlePlan`, `warmNext`),
`provingGround.ts` (moved, not new: `inviteOpen` and `closeInvite` newly exported), the `readsToast` static on a screen

## Numbers provisional

None in the game. The preloader's own: 4 files at a time after the title, 6 for the title, 3 s before it starts
anyway, three tries for a screen's chunk 1.5 s apart (client plumbing, not rules).

## Calls made for Leon (reversible)

1. "Wait for load" read as: nothing but the title's art before the window's load event; and "only the next screen's
   art" as the art of every screen reachable from the one on show (`NEXT`), warmed when the player arrives there.
2. A screen change waits for its chunk with the old screen still up (no loading card); the first visit to a screen on
   a slow link can therefore hold the old screen for the chunk's download time.
3. The Proving Ground's panel chunk is also warmed from the title and the room (both open it).
