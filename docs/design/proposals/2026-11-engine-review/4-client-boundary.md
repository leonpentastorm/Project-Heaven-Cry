# Engine review 4: the web client and its boundary with the engine

12 Nov 2026. Read-only review; nothing was run (a browser suite was in progress), so every "disagrees today" below is **by reading both sides**, not by executing them. Counts are from `grep`/`awk` on the working tree of `claude/charming-gauss-hbq4n0`.

Scope: `apps/web/src/screens`, `templates`, `game/**`, `dc/`, `narrator/**`, `apps/server`, `design/canvas-build/build.py`, `packages/engine/src/index.ts`.

## The short version

The engine does own the dice and the damage. What it does not own is **the question "what can this unit do right now, what does each thing cost, and what would it do?"** That question is answered in about 30 places in the client, each time by gluing together some of the ~60 engine functions the combat screen imports, plus numbers the client typed in by hand. Every system added so far (Sigil, Outburst, Faith, Techniques, Calls, perks, class moves) added its own answer: its own action-id prefix, its own view module, its own block in a 864-line render function, its own branch in the click handler and in Confirm.

The same shape appears three more times:

- **Effects**: the engine emits a flat list of untyped events from 347 call sites; the client works out afterwards which shot belonged to which technique, and how long each thing lasts, in nine files of per-kind constants.
- **The Narrator prompt**: rules the engine already runs are restated in prose, under a cap that has been raised by hand six times.
- **Screen data**: card texts are a committed file generated by a Python script that belongs to the paused canvas.

The fix has one shape too: **the engine describes; the client renders.** An action is a descriptor the engine supplies (name, cost, why not, what to pick, preview). An effect is a typed event inside an action envelope with its timing role. A view is what a player may know, already filtered.

## 1. Rules in the client

### 1.1 What the engine already offers

Previews and views that exist and are used: `previewAttack`, `previewTechnique` / `techniquePad` / `packPad` / `physView`, `previewCall` / `callPad` / `callView`, `previewPerkAction` / `perkActionsFor` / `togglesFor`, `previewDraw` / `previewEvoke`, `previewOutburst` / `previewPump` / `previewOutburstPlan`, `previewPrayer` / `faithView`, `weaponActions` (reload, clear, brace, repair, overwatch, load), `routeHazards`, `worldView`, `cacheView`, `previewOdds`, `approachOptions`, `talkOptions`, `viewFor`.

What does **not** exist: a preview for movement (move, sprint, disengage, prone), for the basic actions (shove, analyze, stim, hide, door, extinguish, escape, recover, shoot an object, pick up, song), or for "where can this action reach". Every hard-coded number below sits in exactly those gaps. The good model is already in the codebase: `weaponActions(u)` (`combat.ts:2359`) returns `{id, label, ap, text, why}` per action and the client just prints it. It covers six actions.

**C. Fog of war (ranked 4)**

`viewFor` (`game.ts:2073-2104`) removes hidden objects, the other side's traps, sight records and notes. It does **not** remove enemy units the viewer's side cannot see. The fight every guest receives holds every enemy's tile, HP, weapon and AP. The client then hides them:

- `combat.js:735` works out sight again (`visibility(cb, 'pc')`) on every render;
- `combat.js:762-765` censors the engine's preview after the fact: it filters `attacks`, `pressure`, `saves` and `moves` by unit id, and filters `notes` **by testing whether the sentence contains an unseen unit's name** (`String(n).includes(nm)`). Two enemies with one name, a name that is a common word, or a note that says "the gunner" defeat it;
- `combat.js:769` builds a second, fogged fight for the Evoke and Outburst previews;
- the comment at `combat.js:759` records the bug that led here (aiming a Lob into fog named the enemies in it).

So fog is a rule the engine owns, implemented as a set of patches in the screen, one per preview. A new previewed system will leak until someone remembers. In a Proving Ground team fight it is also a plain cheat: the other team's positions are in the browser's memory.

### 1.3 The boundary to build

Four engine functions. The client keeps layout, colour, hover, camera and animation; nothing else.

```ts
// 1. What this player may know. Already fogged: units out of sight are absent (or a 'sensed' stub).
viewFor(g, playerId): GameState                       // exists; add the unit filter and stop sending the campaign every time (section 7)

// 2. Everything the acting unit could do, as data.
actionsFor(g, unitId): ActionDescriptor[]

interface ActionDescriptor {
  id: string;                    // 'move', 'tech:main:lunge', 'call:order', 'perk:skill:guts.3:use', 'pray:hymn:2'
  group: 'move' | 'attack' | 'utility' | 'perks' | 'class' | 'sigils' | 'outbursts' | 'calls' | 'faith' | string;
  parent?: string;               // a weapon block, a pad: for nesting
  name: string; text: string;    // from the data, at the tier held
  cost: { ap: number; text: string; other?: { k: string; v: number }[] };   // MP, charge, Momentum, rounds
  why: string | null;            // the engine's refusal now; null = usable
  uses?: { label: string; left: number };
  picks: PickSpec[];             // what to choose, in order
  toggles: { id: string; label: string; on: boolean; why: string | null }[];
  ink?: 'sigil' | 'soul' | 'faith' | 'hostile' | CoreId;   // a meaning, never a colour value
  adjudication: 'engine' | 'hybrid' | 'narrator';
}
type PickSpec =
  | { k: 'unit'; key: string; side: 'enemy' | 'ally' | 'any' | 'self-or-ally'; optional?: boolean; prompt: string }
  | { k: 'tile'; key: string; optional?: boolean; prompt: string }
  | { k: 'option'; key: string; options: { id: string; label: string; text: string; why?: string | null }[]; max?: number }
  | { k: 'text'; key: string; prompt: string };

// 3. What it would do with the picks so far. The engine makes its own copy, binds the game, applies the fog.
previewAction(g, unitId, id, picks, toggles): ActionPreview

interface ActionPreview {
  ok: boolean; why: string | null; ap: number;
  ask: string | null;                         // the next pick, in words; null = ready to confirm
  candidates?: { units?: string[]; tiles?: string[] };   // what may be clicked for the next pick
  reach?: { tile: string; band: number }[];   // the red area, the move range, a Call's range: one field for all of them
  area?: string[]; route?: { tiles: string[]; crosses: { tile: string; what: string }[] };
  affected: { unit: string; tag: string; text: string; tone: 'harm' | 'help' | 'spared' }[];
  rolls: { label: string; pct: number; need: number; terms: Term[]; dmg?: DamageChain }[];
  meters: { k: string; now: number; after: number }[];
  lines: string[];                            // anything else, in words
  action: Action;                             // the exact action to send on Confirm
}

// 4. The per-unit read-out: resources, conditions, Pressure, held Outburst, Faith, what it looks like to this viewer.
unitView(g, playerId, unitId): UnitView
```

Rules for it:

- `previewAction` is the **only** way the client learns a cost, a refusal, a reach or a target. `dryRun`, `dryHeart`, `bindGame`, `fogPv`, `fogCb` and the cost expression at `combat.js:895` are deleted, not wrapped.
- The descriptor returns the finished `Action`. The client never builds a `{type: 'combat/…'}` literal again (39 distinct ones in `combat.js` today).
- The existing per-system previews (`previewTechnique`, `previewEvoke`, `previewPrayer`…) stay as they are **inside** the engine; `previewAction` is an adapter over them. No rules are rewritten. This is why the risk is medium and not high.
- The same two functions serve the story map (`main.js` duplicates the move plan, the reach and the dry run: `main.js:129,925-966`), the turn card (`turnIntro.tsx`), the Proving Ground (`sandbox.tsx`) and the **AI Narrator's `actions[]`** (section 6): the vocabulary a Narrator may use is the list of descriptor ids.

**Pin first:** a golden file. For about 40 saved fights (the `npm run try` scenarios are the source), record today's `actionGroups()` rows (id, label, cost text, why) and today's preview per action. `actionsFor` must reproduce it, minus the six known disagreements, which are fixed on purpose and listed in the commit.

## 3. The effects layer

### 3.1 What is there

- **No schema.** `FxEvent` is `{ n: number; k: string; [field: string]: any }` (`combat.ts:286`). The contract is a 40-line comment (`combat.ts:258-285`) that lists about 75 kinds; the engine emits **122 or more** distinct literal kinds from **347 call sites in 35 files**. `shove` alone is emitted from 21 places, `stance` from 14, `volley` from 11, `heal` from 10.
- **No action structure.** The list is flat. The client rebuilds "these events are one action" by reading the stream in order: `ranged.ts:13-21` says so in its own header ("`tagOf()` reads them in order… keeps each technique's record with its shots and what followed… The guesses (a technique's roll count, chained rolls, one target) stay…"). `melee-techniques.ts` has `meleePrepass`, which rewrites the batch before it is queued (`play.ts:1562`), and private flags stuck on events (`_quick`).
- **Unknown kinds do nothing, silently.** `H[ev.k]?.(ev)` (`play.ts:1480`), and `baseBeat` ends in `default: return 200` (`play.ts:1436`). A kind the engine emits and nobody handles is a 200 ms pause with nothing drawn. This is the mechanism behind "effects that drew the wrong thing": a new technique's events fell through to the plain shot handler.
- **Timing is per-kind constants in nine places.** `baseBeat` (`play.ts:1396-1438`) asks eight modules in a fixed order (`soulBeat`, `feelingBeat`, `classBeat`, `meleeTechBeat`, `rangedBeat`, `physBeat`, `faithBeat`, `worldBeat`), then a 30-case `switch`. When HP bars move is a separate literal: `shot` → the flight time, `melee` → 260, anything else → 80 (`play.ts:1487`). When glyphs disappear is `fxShownGlyphs`; when the log shows is `fxShownLog`; whose turn it "is" on screen is `fxShownTurn`; which tokens are see-through is `fxHeldUnits`. Five separate functions each derive "what the screen should show now" from about 20 module-level mutable maps (`processed`, `queuedTo`, `playedTo`, `waiting`, `walking`, `parked`, `turnShown`, `tileHolds`, `cloudHolds`, `aims`, `looks`, `ghosts`, `lastTok`, `decided`…).
- **Handlers are patched over handlers.** `wrapRanged(H, …)` replaces entries of the table with closures that call the old one "unless the base would show something wrong" (`ranged.ts:8-10, 342-351`). Order of registration is behaviour.
- **Input is gated by playback.** `combat.js:17-22` refuses a player's action while `performance.now() < turnsBusyUntil()`. So a stalled queue is a locked fight, which is why `STUCK_MS`, `STUCK_HARD_MS`, `HOLD_CAP_MS`, `TURNS_HOLD_MAX` and `stall.test.ts` exist.

The layer is 7,027 lines (without tests) and 2,738 lines of tests, and still needed a 2,022-case, 9.5-minute browser sweep to find what was wrong. The sweep found the bugs; nothing in the design prevents the next ones.

### 3.2 The model

Four changes. The first two are the foundation.

**(a) A typed union in the engine.** `type FxEvent = FxShot | FxMelee | FxMove | …`, one interface per kind, exported from one file (`packages/engine/src/fx.ts`), and `emitFx<K extends FxKind>(cb, k: K, data: FxData<K>)`. The 347 call sites then fail to compile when a field is missing or misspelt. The client's table becomes `const H: { [K in FxKind]: (e: FxOf<K>) => void }`: **a kind without a handler is a type error**, not a silent 200 ms. This alone makes "an event nobody draws" impossible. Kinds that are only a state change with no picture get an explicit `noop`.

**(b) An action envelope.** The reducer already knows where an action starts and ends (it calls `trimFx` before each one). Have it stamp every event with `act` (a running number), and emit one opening event per action: `{k: 'act', act, unit, id: 'tech:lunge' | 'attack:burst' | 'evoke' | …, weapon?, targets, tiles}`. Sub-actions nest with `parent` (an Overwatch shot fired inside a move, a reaction, a chain jump). Everything `tagOf`, `meleePrepass`, `rangedBatch`, `sameAction` and the `chain` / `_quick` flags reconstruct is then simply read. The technique's presentation is chosen once, by the envelope's `id`, and receives its child events as a list: it cannot fall through to another technique's picture.

**(c) Timing roles, declared by the engine; durations, owned by the client.** Each event carries a `role`:

- `lead`: wind-up; holds the stage; nothing changes on the board (a draw, an aim, a banner);
- `travel`: something crosses the board; holds the stage; the client derives the time from distance;
- `impact`: the moment results land. **Shown state changes here and only here**;
- `result`: a consequence of the last impact (hurt, cond, down, shield, object broken); plays **at** its impact, holds nothing;
- `aside`: a chip or a word; never holds; never moves the camera.

The client keeps one table `role × kind → ms` (replacing the eight `xBeat` functions and the switch), and one rule: a `result` is scheduled at its parent's `impact`. "The blast played while the grenade was in the air" (`play.ts:1408-1410`) and "the hostiles seemed to attack on your turn" (`combat.js:716`) are both violations of that one rule, fixed by hand per kind today.

**(d) One shown-state reducer.** `stampFxHp` already attaches `hp: {unit: [was, now]}` to the event that caused it (`combat.ts:293-301`). Generalise it: every state change the screen holds back is a delta on an event (`hp`, `pos`, `glyphs`, `log`, `turn`, `objects`). Then

```
shown = applyDeltas(stateBeforeBatch, events with n <= playedN)
```

is one pure function. It replaces `fxShownHp`, `fxShownGlyphs`, `fxShownLog`, `fxShownTurn`, `fxHeldUnits`, the parked and ghost tokens and most of the module-level maps, and it is testable without a DOM. Input gating becomes `playedN === lastN`, with one timeout, in one place.

### 3.3 Why this makes the sweep unnecessary

"Every weapon × technique plays right" splits into three claims:

1. every event the engine can emit has a handler: true by the compiler (a);
2. every technique's events are drawn by that technique's presentation: true by the envelope (b);
3. nothing shows a result before its cause: true by the role rule and the reducer (c, d).

What remains to test is whether each picture looks good, which is a human looking at 30 techniques, not a machine checking 2,022 combinations.

**Pin first:** record the fx stream (JSON) of the sweep's 1,303 played cases once, in the engine, with no browser (`npm run try` can do it). That file is the regression net for (a) and (b): after the change, the same actions must produce the same events plus the envelope. Keep `fx-sweep PARTS=real` (1.5 min) as the one browser check.

**Size L, risk medium.** (a) is mechanical and safe: do it first and alone. (b) is small in the engine and deletes code in the client. (c) and (d) are the real rewrite of `play.ts`'s queue (lines 1440-1745); do them together, behind the recorded streams.

## 7. Multiplayer and server

### 7.1 What happens on one action (`store.ts:219-243`)

1. `apply()` deep-copies the **whole** `GameState` with `JSON.parse(JSON.stringify(...))` (`game.ts:2867`).
2. `viewFor(hostState, me)` for the host's own screen.
3. `persist()`: `JSON.stringify` of the whole state (minus the archive) into `localStorage`, synchronously, on the UI thread. A failed write is swallowed (`store.ts:27`, "full or private mode"). An IndexedDB write follows 400 ms later.
4. `broadcast()`: for **each** guest, `viewFor` and a WebSocket message holding that guest's entire view.
5. The server parses each message, re-stringifies it for the guest and **writes it to Durable Object storage** as `view:<pid>` (`server/index.ts:117-121`). Every 1.5 s the host also sends the whole save, written as `save`.
6. A Narrator turn is four actions in a row (`begin`, `usage`, `turn`, sometimes `error`): four rounds of all of the above.

A view contains `...g`, so it carries the **whole campaign** every time (`m813.json` is 58 KB on disk before expansion), up to 400 story entries, every character sheet, and in a fight the whole `combat` with its log and fx list.

### 7.2 What will not survive

- **Size per action.** Not measured here; a mid-session view is on the order of a few hundred KB (guess from its parts). With 3 guests that is about 1 MB serialised, sent and stored per click, and four times that per Narrator turn. It works now because fights are short.
- **Silent loss at 2 MB.** `server/index.ts:111`: a message over 2,000,000 characters is dropped with no error to anyone. The guest simply stops updating; the 5-second `sync` check asks again and gets the same oversized view. The save has the same limit, so past it the server copy silently stops advancing. A long roguelike run with a generated map is how this gets reached. (The storage backend is SQLite-backed Durable Objects, `wrangler.jsonc:10`; from memory its limit per stored value is also about 2 MB. Verify.)
- **`cb.log` has no bound** inside a fight (`fx` is trimmed to 40 between actions, `combat.ts:305-308`; the log is not), and it rides in every view.
- **Unseen units ride in every view** (finding 4).
- **`localStorage` is about 5 MB per origin** and holds every room's save; the failure is silent.
- **Cost.** Each view is a Durable Object storage write. Fine at this scale; it grows linearly with players × actions.

Host-authoritative relay itself is fine for 4 players. Nothing here needs a new architecture.

### 7.3 The fix, in order

1. **Send the static part once (S).** Split the view into `static` (campaign, anything keyed by a content hash) and `live`. The guest keeps `static` by hash and the host sends it only when the hash changes. Same for the save sent to the server. This alone removes most of every message.
2. **Stop the silent drop (S).** Over the limit, the server answers the host with an error and the host shows it. Log the size of every view in `window.__phc.net()` so it is visible long before the limit.
3. **Fog the view (M, finding 4)** and bound `cb.log` in the view (the last N lines plus a count; the host keeps all of it).
4. **Persist less often (S).** `localStorage` on a 1 s trailing timer and on `pagehide`, not on every action; IndexedDB stays the real save.
5. **Do not store every view on the server (S).** Keep only the latest `save`; on a guest's reconnect with the host away, the guest's own last view in its browser is as good as the server's copy.
6. **Later, if runs get long (M):** send `live` as a patch against the last acknowledged version (`v` already exists and the `sync` message already reports it), falling back to a full view on mismatch. Do this only after 1 to 5; it may never be needed.

**Pin first:** `sync.test.ts`, `store-fight.test.ts`, `store-narrator.test.ts` and `e2e/two-players.mjs` cover the relay. Add one test that a guest that missed the `static` part asks for it and gets it.
