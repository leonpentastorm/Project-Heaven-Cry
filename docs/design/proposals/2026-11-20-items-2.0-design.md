## 1. What you are ruling on

Each line: the question, **the recommended answer**, why. "No answer means yes" applies to every item; nothing goes
live without your word.

1. **One tag kind for grade, or two (grade and rarity)?** **One: `grade`.** In code they are already one value
   (`type Rarity`, `character.ts:164`), and "rare" already means something else in data (how common a round is,
   `rules.json` the enhanced round); two names for one value is the second copy the no-rebuild rule forbids.
2. **Is a grade the instance's or the row's?** **The instance's.** A row is always the Standard; the grade stays in
   `GearState.rarity` (`character.ts:169`) as it does for weapons today; only a unique (later) has a fixed grade. No
   row or id per grade, so old saves and the 72 ids are untouched.
3. **What does a grade give?** **Exactly today's rarity row: accuracy +0/+1/+2/+2/+2, durability x1/1.25/1.5/1.5/1.5,
   price x1/3/8/25/50, damage x1.** The spec's "+1 mod slot" for Fine and Masterwork stays in the spec (the spec wins
   over code in this project): it is not built today (mod slots come from the row only); it is built in stage C when
   the gun ceilings are fitted, behind a data column so it can be 0. Celestial's quirk stays in the spec as "not
   designed"; until then Celestial is Relic stats.
4. **Do armour pieces get grades?** **Yes, where a grade does something: a grade scales a piece's ARMOUR VALUE only,
   through a new column `arm` in the rarity rows (1 for every grade in this pass, fitted in stage C).** The details:
   - Every worn piece with an armour value, and the body armour, carry a grade beside their id (a new optional saved
     field, `wornState`). Body armour's grade is saved under the body slot's key, `wornState.torso_outer` (the slot
     table's body slot: `rules.json` `equipment_slots` lists `torso_outer` and names it `armour_class_from`).
   - A worn piece with no armour value is UNGRADED: a row field `graded: false`, so nobody pays for a grade that does
     nothing. Today that is `field_helmet`, `night_goggles`, `gas_mask`, `utility_belt`, `runner_trousers`,
     `work_gloves`, `field_boots`, `prescription_glasses` and `smiling_mask`; of the new pieces, the three hoods, the
     two optics, `breather`, `sealed_visor`, `rig_belt` and `jump_boots`.
   - The Forge's grade step takes graded armour at the same fees. The Relic step is refused for armour in this pass
     (armour Relic properties come with the uniques patch).
   - The scaling is applied in `gearEffects` (`character.ts:186`), reading the instance's grade from `wornState`.
   Armour does not wear (as today) and takes no mods. S1 paints armour grades and nothing can hold one today
   (`c.worn` is id only, `character.ts:88`); a column of 1s moves no number until balance.
5. **Body armour: how do the Plate and Vest families exist?** **The five classes stay the saved number
   (`armourClass`); the class rows in `rules.json` become the only copy (the typed `ARMOUR` in `character.ts:730` is
   deleted); `breacher_plate` is a class row appended at the end (saved index 6; its armour value is set by the lead in
   step B0); every place code compares class numbers reads a field of the row instead (`>= 5` no sprint at
   `combat.ts:589`, `>= 2` armoured at `classes/k.ts:843`, the class-1 cap at `perks/b.ts:533, 709`); the class rows
   also carry the tag fields (`family`, `form`, `line`), which `itemTags` reads for `armour:<n>`; the Forge can fit
   class 5 at the class row's price (4,000 cr, `rules.json`).** Inserting a class would renumber every save;
   appending does not.

   Agility; hatchet Dexterity / Strength; machete, glaive and hand wraps Raw Power / Strength). New hybrids hit with

   split; the form is a label and never overrides a row.

## 3. The tag system

**The closed list of tag kinds** (data: `rules.json` `item_tag_kinds`, each with an `about`; read by one engine file).
A tag is a `kind:value` string. Code asks for tags, never for an id.

| Kind | Values | Where it lives | Read by |
| --- | --- | --- | --- |
| `kind` | the row's raw data `category`, as it is (for example `light_melee`, `heavy_melee`, `thrown`, `pistol`, `shield`, `armour`, `ammo`, `light`, ...); no mapping table | the row's `category` | pools (they filter on these categories today), the card, the Forge |
| `family` | the 53 family ids (12 melee, 3 shield, 11 armour incl. vests, 17 gun lines, 2 bow, 8 heavy) and `one_off` | row `family`; for body armour, the class row in `rules.json` | the card, pools, family predicates, Weapon Art family cards later |
| `form` | `dex`, `hybrid`, `str` (melee); `close`, `standard`, `long` (guns, bows); `light`, `standard`, `heavy` (shields, armour, heavy families) | row `form`; for body armour, the class row | the card, the validator, the ratio table |
| `line` | maker lines (`legion`, `kemizuchi`, `adamantile`, `hellraiser`, `smetanita`, `adcorp`, `chezknov`, `arsenal`, `albert_town`, `lumeri`, `ork`, `frontier`, `science_team`, `officers`, ...) | row `line`; for body armour, the class row | the card, collections (Gun Nut), later fan hunts |
| `pattern` | a gun's real pattern word, generic | row `pattern` | art and collections only; no rules reader |
| `grade` | standard, fine, masterwork, relic, celestial | the instance (`GearState.rarity`; worn pieces' new state) | accuracy, durability, price, `arm`, the card |
| `slot` | the 12 slots of the slot table | row `slot` | equip, the sheet, the card |
| `role` | words general code asks for: today's row `tags` (`lever`, `electronic`, `evoker_linked`) plus `natural` (fists, beast bite) | row `tags` | Ghost Kill, equip bans, the natural-weapon rules |
| `unique` | true | variants line | the frame and the card; excluded from every rolled pool |

No `explosive` role: rows already carry `explosive: true` (`WeaponDef.explosive`, `data.ts:23`, read by `isExplosive`
(`tactics.ts`, used at `combat.ts:1549`) and the `damage: explosive` predicate); a tag would be its second copy. Whether a piece takes a grade
is the row field `graded` (item 4), not a tag. For `armour:<n>`, `itemTags` reads the tag fields from the class row in
`rules.json` (body armour has no items row).

`weapon_art` is a field, not a tag: null on every family row, every item row and every variants line in this pass;
the validator refuses any other value until the Weapon Art patch. The instance gets the optional saved field
`GearState.weapon_art` in stage A, null and never written in this pass. Whether a Masterwork-or-better weapon's own
card belongs to the row or the instance is item 22.

## 4. Families and grades

**The rule in words.** A weapon, shield or armour piece belongs to one family and is one of its three forms. The
family is data (one table): its name, maker line, signature, the forms' techniques (the one copy: a row names a
technique only to override it), and its Weapon Art slot. Each row still carries its own full numbers; the hit skill
is the row's `phys.hits_with` alone (`skill` leaves the rows); the validator refuses a row whose form disagrees with its family (a Dexterity form
must hit with Dexterity and grow with Agility; a Strength form Raw Power and Strength; a hybrid any of the three
patterns in use). A form's second skill is an alpha skill or none (R5) and feeds the family signature, never the hit.

**Grades in words.** A row is the Standard. An instance carries a grade; every grade number is read from the rarity
row and applied to the Standard row where it is read today (accuracy at the attack roll, durability at `maxDurOf`,
price at `priceOf`; armour through the new `arm` column, applied in `gearEffects` reading the instance, and only to
a piece's armour value; a worn piece with no armour value is ungraded, item 4). No grade pictures
are needed to play: the card shows the Standard picture with the grade word and marks.

Tables: `2026-11-20-items-2.0-tables.md` sections 1 (grades), 2 (melee), 3 (shields), 5 (guns and bows), 6 (heavy).

## 5. Armour and slots

- **One slot table in data** (id, saved key, label, order), read by engine and client; the client's copies
  (`main.js:73 WORN_SLOT`, `:119 SLOTS`) are deleted. Today `rules.json equipment_slots` is read by nothing but a
  validator line, and its spelling has drifted (`torso_inner` against the saved `inner_torso`; `classes/j.ts:372`
  tests both).
- **Worn pieces:** a worn piece is its row's `effects`, summed by `gearBonus` (`character.ts:191`) through the ops
  that exist (`armour_bonus`, `injury_resist_bonus`, `movement_bonus`, `carry_bonus`, `dark_sight`, `hazard_immune`,
  `ignore_difficult`, `unarmed_damage_bonus`). Armour numbers are scaled by level at `armourOf`
  (`character.ts:737-739`).
