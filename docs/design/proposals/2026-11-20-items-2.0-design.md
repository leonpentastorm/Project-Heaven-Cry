# Items 2.0: design for sign-off (20 Nov 2026)

The one document Leon rules on before any Items 2.0 builder starts. It follows his rulings of 20 Nov
(`2026-11-20-items-2.0-plan.md`): placeholder pictures; Weapon Arts not usable (balance leaves their room, an item
carries an empty slot); the 23 uniques cut but carried later as data rows; grades a rule from the Standard row;
content is data, code reads tags and never ids. Facts were checked on `release/0.33` (commit `957d14f53`); where a
design input and the code disagree, the code is written here and the input is named stale. Long tables:
`2026-11-20-items-2.0-tables.md`.

## 1. What you are ruling on

Each line: the question, **the recommended answer**, why. "No answer means yes" applies to every item; nothing goes
live without your word.

1. **One tag kind for grade, or two (grade and rarity)?** **One: `grade`.** In code they are already one value
   (`type Rarity`, `character.ts:164`), and "rare" already means something else in data (how common a round is,
   `rules.json` the enhanced round); two names for one value is the second copy the no-rebuild rule forbids.
2. **Is a grade the instance's or the row's?** **The instance's.** A row is always the Standard; the grade stays in
   `GearState.rarity` (`character.ts:169`) as it does for weapons today; only a unique (later) has a fixed grade. No
   row or id per grade, so old saves and the 72 ids are untouched.
3. **What does a grade give?** **Exactly today's rarity row: accuracy +0/+1/+2/+2/+2, durability x1/1.25/1.5/1.5/1.5,
   price x1/3/8/25/50, damage x1.** Strike the spec's "+1 mod slot" for Fine and Masterwork and the Celestial "quirk"
   from the spec table and the `rules.json` note; Celestial is Relic stats until a quirk is designed. The code gives no
   slot today (mod slots come from the row only) and adding one moves the gun ceilings stage C fits.
4. **Do armour pieces get grades?** **Yes: every worn piece and the body armour carry a grade beside their id (a new
   optional saved field), the Forge's grade step takes them at the same fees, and a grade multiplies the piece's armour
   by a new column `arm` in the rarity rows, set to 1 for every grade in this pass and fitted in stage C.** Armour does
   not wear (as today) and takes no mods. S1 paints armour grades and nothing can hold one today (`c.worn` is id only,
   `character.ts:88`); a column of 1s moves no number until balance.
5. **Body armour: how do the Plate and Vest families exist?** **The five classes stay the saved number
   (`armourClass`); the class rows in `rules.json` become the only copy (the typed `ARMOUR` in `character.ts:730` is
   deleted); `breacher_plate` is a class row appended at the end (saved index 6; armour value not decided, between 15
   and 20); every place code compares class numbers reads a field of the row instead (`>= 5` no sprint at
   `combat.ts:589`, `>= 2` armoured at `classes/k.ts:843`, the class-1 cap at `perks/b.ts:533, 709`); the Forge can fit
   class 5 (price not decided, stage C).** Inserting a class would renumber every save; appending does not.
6. **What does a hybrid form hit and grow with?** **Every existing row keeps its own (katana and gladius Dexterity /
   Agility; hatchet Dexterity / Strength; machete, glaive and hand wraps Raw Power / Strength). New hybrids hit with
   Dexterity and grow with Strength: `trench_knife`, `dock_cutter`, `kemizuchi_side_sword`, `war_hammer`,
   `adamantile_longsword`, `weighted_gloves`.** File 05 says only "between the two"; the hatchet is the one honest
   split; the form is a label and never overrides a row.
7. **Can the Forge re-align a weapon to another attribute (the "realign" audit)?** **Not in this pass.** Today scaling
   and the hit skill are read from the row by id only (`weaponMult`, `character.ts:767`; `weaponVia`,
   `combat.ts:1586`); an override per instance touches six functions and the saved shape, and the hit skill has two
   copies (`skill` and `phys.hits_with`, equal on all 72 rows) that must become one first. If you want it later, it is
   a variant line (a new form kind setting both), not instance state.
8. **AP and hands of the new melee forms?** **Dexterity and hybrid forms `light_melee` (2 AP); Strength forms
   `heavy_melee` (3 AP, one-handed ones included, as `ork_machete` today); gloves `unarmed`; the two-handed Dexterity
   forms (`legion_spear`, `adamantile_plate_needle`) `light_melee` two-handed, and one-handedness is read from the row's
   `hands` (the category list `ONE_HANDED`, `character.ts:721`, is deleted).** Melee AP is set by category
   (`combat.ts:1389`); "hit quick" is the file's own word. Side effect: `ork_machete` (one-handed `heavy_melee`) starts
   counting as one-handed for the arm-injury penalty; the builder lists every row whose answer changes before
   changing it.
9. **Versatile grip (`war_hammer`, `adamantile_longsword`)?** **Ship both one-handed; versatile grip waits.** No field
   exists for it and two rows do not earn a new primitive in this pass.
10. **Signatures and second skills: what is built now?** **The second skill is a row field from stage A. A family's
    signature and a form's second-skill effect are built in stage B only where an existing primitive carries them;
    otherwise the row ships as a plain playable weapon and the card does not mention the missing effect (never
    `built:false`, which hides the row from every pool, and never a text with no reader). Where the files give no
    threshold (all 34 gun and bow variants of files 06 and 10), the effect starts at 5 points of the second skill
    (file 09's commonest).** Ruling 1 is "only the stats need to work to test"; a plain row tests stats, and each
    missing signature is listed for its own primitive approval.
11. **Who sets the numbers of the 87 new rows?** **The lead writes one per-form ratio table before any row (damage,
    range, magazine, weight, price; close / standard / long and Dexterity / hybrid / Strength; and, for families with
    no existing row, which existing row is the source); a Sonnet builder fills the rows from it; every number
    PROVISIONAL; stage C fits.** No file gives a number; one table is one copy of the rule. The ratios themselves are
    not decided and are the lead's first stage B job.
12. **R5 sweep: remove `phys.also_scales` from `fists`, `knuckledusters`, `hand_wraps`, `iron_mitts` and
    `hellraiser_servo_fist`?** **Yes.** R5 says a base rolls its own skill; the melee profile's skill slope is 0, so no
    number moves (the golden tables prove it in the same commit).
13. **Shields: the Heavy word and the pavise?** **Heavy is a property on `ram_plate`, `barrier_wall` and `pavise`,
    -0.5 Movement each, two stack (PROVISIONAL); `riot_shield` keeps its own -0.5 and is not Heavy. The pavise becomes
    buyable as a plain Heavy Guard shield; its "plant it" text is cut and recorded as owed.** -0.5 matches the riot
    shield and armour classes 3 and 4; planting needs a map-object primitive the Outpost Wall unique also needs, so it
    belongs to the uniques patch. Ward soak is `damage_reduction` with the `damage` predicate (`ranged`,
    `elemental`), numbers not decided; Guard / Strike / Ward plate and follow numbers are not decided (stage C).
14. **Hoods and optics: build them, or cut them?** **Build them on stats that exist: the three hoods `stat_mod` on
    `seen_range` (negative: harder to see), the monocle and sight visor `stat_mod` on `vision`. It needs primitive N4
    (a worn piece's item ops are heard; section 7). Numbers not decided (stage C).** If you refuse N4, the five pieces
    (`cowl`, `hood`, `blackout_hood`, `spotters_monocle`, `sight_visor`) are cut from this pass rather than shipped
    doing nothing.
15. **How will a unique be added later?** **As one `data/variants.json` line: a base row, the existing modifier
    kinds, its own extra effects, a fixed grade Relic, the tag `unique`, never rolled in loot or shops, and an empty
    Weapon Art slot. `homecoming` (the harpoon gun, no family) gets its own base row with family `one_off`.**
    `variants.ts` already clones a row, names it, fixes its grade and holds its modifiers only in a hand
    (`with_this`); a second mechanism would be a rebuild seed.
16. **Do enemies get the new forms in this pass?** **No: enemy weapon pools stay id lists in `data/survival.json`
    (data, allowed); new forms reach enemies in stage C as data lines.** Changing pools moves the replays and run
    baselines twice.
17. **The Forge's grade step: flat fee or price difference?** **Keep the flat fee (1,500 / 3,500 / 6,500,
    `survival.json grade_up`).** It is a service fee, not a second item price; changing it is balance.
18. **Torch and flare: the shop sells them with texts promising damage, Burning, a throw and reveal-Hidden that
    nothing builds.** **Cut both texts to what is built (a light radius on dark maps) and keep them in the shop; the
    rest is recorded as owed.** The light works (`combat.ts:587`, `litAt`); a text with no reader is the defect.
19. **Ration pack, chalk and wax, prayer beads: icons, no reader, not obtainable in Survival.** **Keep the rows; their
    text says "a carried good: nothing uses it", as the cigarettes' already does.** No code, no replay risk; a reader
    for each belongs to the system that would use it (rest, Sigils by hand, prayer).
20. **The 5 orphaned perk icons: reuse?** **Yes, as the pictures of Objection! (`burden-of-proof`), Five Stars
    (`rally-cry`), Nobody Left Behind (`soulmate`), Smooth (`sweet-talker`) and Point Man (`you-get-used-to-it`).**
    They are Wick pictures of fitting subjects and their own perks no longer exist (the audit found 5, not 11).
21. **Figment order and trait icons (19 + 22 pngs, delivered, never loaded): wire them?** **Yes, as a small separate
    Sonnet lane in the same release: one build rule and a png reader in `figmentIcons.ts`.** `data/figments.json`
    already names 8 of them and those slots show nothing today. Hard Light and Sharp Light do not take the order
    pictures: the order slots keep their own.

## 3. The tag system

**The closed list of tag kinds** (data: `rules.json` `item_tag_kinds`, each with an `about`; read by one engine file).
A tag is a `kind:value` string. Code asks for tags, never for an id.

| Kind | Values | Where it lives | Read by |
| --- | --- | --- | --- |
| `kind` | weapon, shield, armour, focus, quiver, mod, round, consumable, tool, material, food, document, loot, augment, companion | the row's `category` | pools, the card, the Forge |
| `family` | the 53 family ids (12 melee, 3 shield, 11 armour incl. vests, 17 gun lines, 2 bow, 8 heavy) and `one_off` | row `family` | the card, pools, family predicates, Weapon Art family cards later |
| `form` | `dex`, `hybrid`, `str` (melee); `close`, `standard`, `long` (guns, bows); `light`, `standard`, `heavy` (shields, armour, heavy families) | row `form` | the card, the validator, the ratio table |
| `line` | maker lines (`legion`, `kemizuchi`, `adamantile`, `hellraiser`, `smetanita`, `adcorp`, `chezknov`, `arsenal`, `albert_town`, `lumeri`, `ork`, `frontier`, `science_team`, ...) | row `line` | the card, collections (Gun Nut), later fan hunts |
| `pattern` | a gun's real pattern word, generic | row `pattern` | art and collections only; no rules reader |
| `grade` | standard, fine, masterwork, relic, celestial | the instance (`GearState.rarity`; worn pieces' new state) | accuracy, durability, price, `arm`, the card |
| `slot` | the 12 slots of the slot table | row `slot` | equip, the sheet, the card |
| `role` | words general code asks for: today's row `tags` (`lever`, `electronic`, `evoker_linked`) plus `explosive`, `natural` (fists, beast bite), `graded: false` families' rows | row `tags` | the explosive perks, Ghost Kill, equip bans, the Forge's grade step |
| `unique` | true | row or variants line | the frame and the card; excluded from every rolled pool |

`weapon_art` is a field, not a tag: null on every family row and every item row in this pass; the validator refuses
any other value until the Weapon Art patch. (Weapon Arts Decided 1: a Standard weapon uses its family's card, a
Masterwork or better has its own; so the slot exists on the family row and on a unique.)

**Example 1: an ordinary new weapon, `dock_cutter`** (Cavalry blades, hybrid form). Numbers marked "ratio" come from
the stage B ratio table; none is decided here.

```json
{
  "id": "dock_cutter", "type": "dock_cutter", "name": "Dock cutter",
  "category": "light_melee", "hands": "1H", "weight_kg": 1.6,
  "family": "cavalry_blades", "form": "hybrid", "line": "officers", "second_skill": null, "weapon_art": null,
  "damage": "ratio", "ap_cost": { "attack": 2 }, "price_credits": "ratio", "durability": "ratio",
  "mod_slots": ["edge", "grip"], "skill": "dexterity", "mastery_family": "light_blades",
  "phys": { "system": "melee", "profile": "melee", "props": ["light", "edge"],
            "hits_with": "dexterity", "scales_with": ["strength"], "teaches": "the family's (data, families table)" },

```

`itemTags` gives `kind:weapon, family:cavalry_blades, form:hybrid, line:officers, grade:standard, slot:main_hand`; at
a Fine grade the instance gives `grade:fine` and everything else is unchanged.

**Example 2: a unique as it WOULD be added later, Grandmother's Teeth** (Ork cutters, built on `ork_machete`). One line
in `data/variants.json`; nothing else in the repo changes for it except what its own new effect needs.

  "rarity": "relic", "unique": true, "line": "ork", "patron": null,

variants line (validated), and its `weapon_art` filled in.

## 4. Families and grades

**The rule in words.** A weapon, shield or armour piece belongs to one family and is one of its three forms. The
family is data (one table): its name, maker line, signature, the forms' techniques, and its Weapon Art slot. Each row
still carries its own full numbers; the validator refuses a row whose form disagrees with its family (a Dexterity form
must hit with Dexterity and grow with Agility; a Strength form Raw Power and Strength; a hybrid any of the three
patterns in use). A form's second skill is an alpha skill or none (R5) and feeds the family signature, never the hit.

**Grades in words.** A row is the Standard. An instance carries a grade; every grade number is read from the rarity
row and applied to the Standard row where it is read today (accuracy at the attack roll, durability at `maxDurOf`,
price at `priceOf`, armour at `classArmour` and the worn-piece sum through the new `arm` column). No grade pictures
are needed to play: the card shows the Standard picture with the grade word and marks.

Tables: `2026-11-20-items-2.0-tables.md` sections 1 (grades), 2 (melee), 3 (shields), 5 (guns and bows), 6 (heavy).

## 5. Armour and slots

- **One slot table in data** (id, saved key, label, order), read by engine and client; the client's copies
  (`main.js:73 WORN_SLOT`, `:119 SLOTS`) are deleted. Today `rules.json equipment_slots` is read by nothing but a
  validator line, and its spelling has drifted (`torso_inner` against the saved `inner_torso`; `classes/j.ts:372`
  tests both).
- **Worn pieces:** a worn piece is its row's `effects`, summed by `gearBonus` (`character.ts:191`) through the ops
  that exist (`armour_bonus`, `injury_resist_bonus`, `movement_bonus`, `carry_bonus`, `dark_sight`, `hazard_immune`,
  `ignore_difficult`, `unarmed_damage_bonus`). Armour numbers are scaled by level at `armourOf`
  (`character.ts:737-739`).
- **Worn-piece state:** `Character.wornState?: Record<slot, GearState>` beside `worn`, the way `weaponState` sits
  beside `weapon`: optional, absent means Standard, written only when a piece is not Standard; it moves with equip,
  take off, give and the pack.
- **Body armour:** the class number stays; the class rows are the only copy; the breacher plate is class 6; the
  Forge fits up to class 5; class 5's `no_sprint` is read from its row (today the typed `>= 5`).
- **Reachable in Survival today:** the camp shelf holds 5 pieces and `armour:1`; the Forge's rolled stock can offer 14;
  the shop's rolled pool never holds armour. That stays; the new pieces join the Forge pool through `itemsWith`.
- **Two screen faults fixed with the card lane:** the sheet's STATUS tab shows no Armour line (`derived.ts:26`), and
  the GEAR tab shows the class value unscaled (`main.js:619`) where the fight uses the level-scaled one. Both read the
  engine's `armourOf`.

The 30 armour forms by slot: tables section 4.

## 6. The item card

**One view-model, one component.** The engine's `gearPreview` (`gearpreview.ts`) already makes the numbers of every
card (shop, camp, rewards, Forge, compare); it gains: the grade word and marks from the rarity rows, the tags, the
family and form names, the second skill (shown only when its effect is built), and the picture id. The client gets one
card component, used by the six layouts that draw items today (shop card, upgrade card, reward offer, loadout pick and
shelf cards, Give rows, sheet tips). No number is worked out in the client.

**Picture chain (placeholder by tag, never by id):** the item's own picture; else its variant's base; else the
family's Standard form; else a plain glyph for its `kind`. A missing picture never blocks a row.

**What the card shows:** name, picture, family and form ("Cavalry blades, hybrid"), maker line, grade word and marks,
the numbers `gearPreview` gives (damage, hit chance, AP, range, magazine, Defense, Armour, weight, durability), the
signature line only if built, mods and the Relic property. The Weapon Art slot is not drawn in this pass.
