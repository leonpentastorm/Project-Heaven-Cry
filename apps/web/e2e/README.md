# End-to-end tests

Real browsers play the game: the Proving Ground alone, or two players in a room through the relay, with the scripted
Narrator (no API key needed). Each `*.mjs` here is one suite; `lib.mjs` is what they share.

**The rule of this folder: every suite is in a group and green, or it is deleted. A red run means a real bug.**

## Running them

```bash
npm run e2e -- smoke              # five suites that catch most breakage
npm run e2e -- tabs faith         # the suites you name
npm run e2e -- rules              # every suite that checks rules and screens
npm run e2e -- anim               # every suite that looks at animation or time
npm run e2e -- all                # rules + anim: every suite in this folder
npm run e2e -- sweep              # fx-sweep's whole table (about 17 minutes)
npm run e2e -- --list             # the groups
```

`tools/e2e.py` builds the game, starts the room server on port 8787 (and starts it again if it dies), runs the suites
three at a time, prints one line a suite, and stops the server. Logs: `.check/e2e/<suite>.log`. Options: `--jobs N`, `--no-build`, `--slow`,
`--no-retry`, `--base URL`.

**The groups** are in `groups.json`, and nowhere else:

- `rules`: suites that check rules and screens. The runner sets `FAST=1` for them: a fight plays every effect in order
  about 25 times faster (`game/combatSpeed.ts`, the hidden `test` speed).
- `anim`: suites that look at an animation part-way through, or at how long something takes. They run at the
  player's real speed.
- `all` is `rules` + `anim`. `smoke` is a few of them. `sweep` is `fx-sweep` with its whole table (everywhere else
  `fx-sweep` plays its real-speed, fog and glyph parts).

**Every suite must be in `rules` or in `anim`.** `tools/e2e.py` refuses to run when a `.mjs` file here is in neither,
and `npm run check` fails for the same reason (`apps/web/src/e2e-groups.test.ts`). A suite nobody runs rots: on 12 Nov
2026, 32 of 64 suites were in no group; run beside each other, 17 of those 32 did not pass, 12 of them not even alone.

**The retry rule.** A suite that fails while others run beside it is run once more, alone, after the rest.

| The line says | It means | Do |
| --- | --- | --- |
| `ok` | passed | nothing |
| `FLAKY … passed alone` | it failed beside the others and passed alone. The run still ends green (`GREEN, BUT n PASSED ONLY ALONE`) | not a bug in the game: a fault in the SUITE (it cannot share a machine). Fix the suite with the checklist below. The first run's log is `.check/e2e/<suite>.first.log` |
| `FAIL … alone too` | it failed twice, the second time with the machine to itself | a real bug, in the game or in a stale suite. The run is red |
| `ok … run again: the room server had stopped` | `wrangler dev` died in the middle of the run, or the disk was full (see Disk, below). The runner started the server again and ran the suite again; that run counts | nothing; the run's last line says how often it happened |

A suite never gets a second retry, and a suite that prints no `ok` line fails ("nothing was checked"). A suite that
runs for 30 minutes is stopped with its browsers and fails.

## A suite that does not flake: the checklist

A suite flakes when it measures the machine and not the game. Every item below is a way that happened here.
Read it before you write or change a suite; `apps/web/src/e2e-groups.test.ts` enforces items 1, 2 and 8.

1. **Never sleep on the script's clock.** `page.waitForTimeout(ms)` is not used in this folder (the count is 0 and a
   test keeps it there). It waits a number of milliseconds in THIS script, while the game runs in another process: on a
   busy machine the game is not ready when the sleep ends.
2. **Wait for the state, with a long timeout.** `await until(page, () => <what you wait for>)` (lib.mjs). A timeout
   only costs time when the thing never comes, and then the suite is red for a reason. A wait that fails when its
   time runs out gets at least 30 s; shorter is a wall-clock assertion in disguise (a page reload took 20 s beside two
   other suites on a busy machine). A wait followed by `.catch(() => {})` is an optional wait, "if it comes", and may
   be shorter. `page.goto` and `page.reload` on a page from `player()` already wait for the game's first screen.
3. **After a click or an action, when you can't name the state: `await settle(page, ms)`.** It waits `ms` on the PAGE's
   clock, then until the effects queue has nothing left and two frames pass with nothing added to the page. In a fight,
   `await fxIdle(page)` waits until every effect has played and the input hold is over.
4. **Inside an animation: `await pause(page, ms)`**, a timer in the page. The page runs its own shorter timers before
   it, so "600 ms after the click" still means "after everything the game planned for the first 600 ms".
5. **Something that is on screen for a short time is looked at IN the page, by a watcher started BEFORE the click.**
   A cut-in lasts 1.4 s; a round trip from this script can take that long on a busy machine. Use a `MutationObserver`
   in `page.evaluate` that writes what it saw to `window` (`cutins.mjs` spy(), `slate-stamp.mjs` watchStamp(),
   `faith-pg.mjs` `__cutFacts`), or `watch(page, name, selector)` from lib.mjs. Read all the parts of a short-lived
   thing in ONE `page.evaluate`, never one locator call after another.
6. **ORDER and PRESENCE are judged from the plan, not from a stopwatch.** The effects layer records what it drew and
   when it was DUE: `traceStart(page)`, then `traceTake(page)` gives `{ w, n, t, rt }` (`fx/dom.ts trace()`). `t` is the
   plan and is the same on any machine; `rt` is when it ran. "The hit comes after the shot" is `hit.t >= shot.t`.
   `fx-sweep.mjs` judges every weapon × technique this way.
7. **A wall-clock assertion stays only where the time IS the thing under test** (how long the words of a cut-in stay
   readable). Then: measure in the page (`watch()` / `watched()`); **the lower bound is the plan's, exactly (a timer
   never fires early); the upper bound is twice the plan plus a second or two**; and a comment starting `WALL CLOCK, on
   purpose` says why. The exact length belongs in a unit test with a fake clock (`apps/web/src/game/**/*.test.ts`).
8. **Print named checks**: `ok('what was looked at (' + what was seen + ')', condition)`. Put the value in the label:
   the failing line must say what was there.
9. **A check that only reads `window.__phc.getState()` after an action is an engine test paying for a browser.**
   Write it in `packages/engine/test/` (`fightWith`, `npm run try`). A suite checks what is drawn and clicked.
10. **Set the fight up from what is there, not from tile names.** The Proving Ground is 26 × 26 with crates in rows,
    sides start 10 to 14 tiles apart and hostiles out of sight are Hidden. Find a free tile beside your unit in the
    page; check the set-up with its own `ok` line (a hostile in sight, a clear lane) so a stale set-up reads as one.
11. **Nothing reaches the outside.** Stub every provider address the suite could call (`page.route`).
12. **Run it beside something heavy before you call it done,** three times:
    `npx vitest run --root packages/engine & npm run e2e -- <your suite> tabs perks`. `FLAKY` is not done.

## Running one by hand

```bash
npm run dev -w @phc/server                      # after `npm run build`; http://127.0.0.1:8787
node apps/web/e2e/two-players.mjs
FAST=1 node apps/web/e2e/tabs.mjs               # a `rules` suite, as the runner runs it
BASE=https://project-heaven-cry.leonpentastorm.workers.dev node apps/web/e2e/reconnect.mjs
```

`PARTS` means one thing to `fx-sweep` (`real,table,fog,glyphs`) and another to `coop-stall` (`ABC`). The runner passes
a `PARTS` you set only when you ask for ONE suite (`PARTS=table npm run e2e -- fx-sweep`, `PARTS=BC npm run e2e --
coop-stall`). (Set for a whole run, it once made `coop-stall` run none of its parts and print `RESULT OK`; a suite that
prints no `ok` line now fails.)

**Proxies:** with `BASE` and `HTTPS_PROXY` both set, `lib.mjs` sends Chromium through `HTTPS_PROXY` (an agent sandbox's only way to the live site), with loopback bypassed. A `BASE` on this machine (`127.0.0.1` or any `127.x`, `localhost`, `::1`) never goes through the proxy, so a local `wrangler dev` runs the same with `HTTPS_PROXY` set or not (such a proxy only takes CONNECT to the outside, and every local test used to stop at the title):

```bash
BASE=http://127.0.0.1:8797 node apps/web/e2e/ground.mjs   # HTTPS_PROXY may stay set
```

Screenshots land in `apps/web/e2e/shots/`, or in `SHOTS=<dir>` when it is set (`OUT` in lib.mjs follows it). The runner
gives every suite its own folder, `.check/e2e/shots/<suite>/`, and empties it when the suite passes (`KEEP_SHOTS=1`
keeps them): a full run's pictures are 200 MB. Playwright is loaded with `require('playwright')`.

**Disk.** A full disk fails every suite within seconds ("Target crashed", then the room server stops): three suites'
browsers write a few hundred MB of profiles and cache while they run. The runner refuses to start on a nearly full
disk, puts the browsers' temp folder on the memory disk (`/dev/shm`) when the disk has under 4 GB free, and runs a
suite again when the disk was full under it.
